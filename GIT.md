# Правила ведения Git

Цель: в любой момент можно откатиться к рабочему состоянию, а к сдаче — показать
организаторам внятную историю разработки (git входит в обязательный пакет
материалов, без него решение к валидации не допускается).

Правило простое: **закончил действие — коммить.**

## Что считается «действием»

Один логический шаг, после которого проект в осмысленном состоянии: добавил модуль,
починил баг, обновил документ, собрал новый дек, получил новый результат эксперимента.
Не копи изменения из разных задач в один коммит — откатывать такой коммит больно.

## Формат коммита

```
<поток>: <что сделано>
```

Префиксы по рабочим потокам из `PLAN.md`:

| Префикс | Поток |
|---|---|
| `sim:` | ГГДМ: дек, SUMMARY, запуск симулятора, выгрузка результатов |
| `eco:` | ЧДД: обвязка эталонного расчётчика, нормативы, паритет |
| `sch:` | генерация и валидация `wells_schedule.inc` |
| `srg:` | суррогатная модель: DoE, датасет, обучение, метрики |
| `mas:` | агенты, оптимизация, логика принятия решений, объяснимость |
| `ui:` | веб-платформа, визуализация |
| `docs:` | отчёт, README, презентация, схемы, журнал экспериментов |
| `infra:` | окружение, зависимости, CI, Docker, гит |

Примеры: `sim: SUMMARY-секция под 14 колонок расчётчика`,
`eco: тест паритета с эталоном на примере исходных данных`,
`sch: запрет WLPR > 500 м3/сут при записи WCONPROD`.

## Ветки

- `main` — всегда рабочее состояние: сквозной прогон запускается, тесты проходят.
- Крупная или рискованная работа — в ветке `<поток>/<тема>` (например,
  `srg/lstm-baseline`), в `main` через merge после проверки. Мелкие безопасные шаги
  можно коммитить в `main` напрямую.
- Историю, отправленную в общий репозиторий, не переписываем (`push --force` в `main`
  запрещён).
- Перед push **ветки, отличной от `main`**, проверить её собственную версию
  `.github/workflows/ci.yml`: старые ветки несут свои триггеры и свои пины, состояние
  `main` о них ничего не говорит.

## Что НЕ кладём в репозиторий

- **Виртуальное окружение.** Живёт в `.venv/` и только там — этот путь в
  `.gitignore`. В корне проекта venv не создаём: под Windows его каталог
  называется `Scripts/`, файловая система считает его тем же путём, что наш
  `scripts/`, и правило `/Scripts/` до 16.08 молча выкидывало из репозитория все
  скрипты запуска. Обратная сторона того же совпадения — `import scripts.*`
  переставал работать без `PYTHONCASEOK=1`, то есть тесты шли не так, как у
  проверяющего. 23.08 окружение перенесено в `.venv/`, правила-заплатки из
  `.gitignore` убраны. Проверить перед первым коммитом:
  `git status --short | head -50` не должен показывать ни `Lib/site-packages`,
  ни `.exe` в `scripts/`.
- **Записи лекций.** Три `.webm` — около 2 ГБ, в GitHub не помещаются. В
  репозитории — расшифровки (`docs/method/transcripts/`) и ссылки
  (`docs/materials.md`).
- **Распакованный дек.** `Model_Z_grid.inc` — 74 МБ россыпью; в `.gitignore`.
  **Архивы дека при этом в репозитории есть** и лежать там должны:
  `materials/Model_Z.zip` (16,9 МБ) и `materials/Model_Z_final_OPM.zip`
  (17,6 МБ) — сжатыми они помещаются, а проверяющему не приходится искать
  поставку по каналу связи (`README.md`, раздел «Установка»).

  До 21.08 здесь стояло «дек в репозиторий не кладём», хотя он лежит там с
  15.08 и `README.md` велит распаковывать его именно оттуда. Правило и репозиторий
  разошлись на шесть дней; исправлено правило, потому что практика оказалась
  удобнее для проверяющего.
- **Результаты прогонов симулятора** (`.UNSMRY`, `.UNRST`, `.EGRID`, рестарты) и веса
  моделей. В репозитории — конфиг, seed и команда, которой прогон воспроизводится.
- Исключение: `vendor/CHDD_PYTHON/` — эталонный расчётчик ЧДД организаторов
  коммитим целиком и побайтово. Он маленький и он — источник истины по деньгам.

## Ремоуты

Пушим в **оба** репозитория, истории обязаны совпадать: `true` — командный репозиторий
у организаторов, `origin` — наше зеркало. Настроить один раз у каждого участника
(URL — в `docs/materials.md`, подставить фактические):

```bash
git remote add true  <URL репозитория организаторов>
git remote set-url --push true <URL репозитория организаторов>
git remote set-url --add --push true <URL зеркала>
```

Тогда обычный `git push` уходит в оба сразу. Проверить расхождение и догнать
отставший репозиторий:

```bash
git ls-remote true main          # хеши HEAD в обоих...
git ls-remote origin main        # ...должны совпадать
git push true main
git push origin main
```

Если push прошёл только в один (сеть отвалилась, у кого-то настроен один push-URL) —
чиним немедленно, досылая недостающие коммиты. `push --force` для выравнивания не
применяем.

## Первый запуск на новой машине

На чистой Windows-машине git встаёт трижды подряд, и каждый раз не по вине
репозитория, поэтому три шага стоит сделать ДО работы.

**1. Один раз войти интерактивно.** Свежий Git for Windows несёт настроенный
`credential.helper=manager`, но без сохранённой учётки. В неинтерактивной сессии он
пытается открыть графическое окно логина, которого никто не увидит, и любая сетевая
операция **виснет вместо того, чтобы упасть** — это легко принять за медленную сеть.
Диагноз виден так:

```
GIT_TERMINAL_PROMPT=0 git fetch --all
fatal: could not read Username for 'https://github.com': terminal prompts disabled
```

Лечится одним `git push` руками из обычного терминала с прохождением диалога; дальше
учётка лежит в Windows Credential Manager.

**2. Задать identity**, иначе первый же коммит падает с `Author identity unknown`:

```
git config --global user.name  "Имя Фамилия"
git config --global user.email "you@example.com"
```

`--global`, а не локально: при следующем checkout то же самое всплывёт заново.

**3. Добавить ремоут `true`** — в свежем клоне есть только `origin`, то есть отправить
что-либо организаторам нельзя, и требование «истории совпадают» становится
непроверяемым.

Отдельно: на Windows `git` может не быть в `PATH` у PowerShell (лежит только в Git
Bash). Команды из README тогда не выполняются — добавьте `C:\Program Files\Git\cmd`.

## Вехи

Достигли этапа из `PLAN.md` — ставим тег:

```
git tag -a v0.1-baseline -m "Базовый сценарий посчитан, ЧДД зафиксирован"
git push --tags
```

Отдельно тегируем **каждую отправку организаторам**: тег вида
`submit-2026-08-17`, и в его сообщении — заявленный ЧДД и путь к
`wells_schedule.inc`. Сдали — значит, состояние репозитория в этот момент
воспроизводимо навсегда: при расхождении цифр это единственный способ доказать, чем
считали.

## Как откатываться

| Ситуация | Команда |
|---|---|
| Посмотреть историю | `git log --oneline` |
| Испортил файл, ещё не коммитил | `git restore <файл>` |
| Вернуть файл из прошлого коммита | `git restore --source <hash> <файл>` |
| Отменить коммит (безопасно, новой записью) | `git revert <hash>` |
| Снести локальные незакоммиченные изменения | `git reset --hard` (осторожно, необратимо) |
| Посмотреть проект на момент коммита | `git checkout <hash>`, назад: `git checkout main` |

По умолчанию — `git revert`: он не переписывает историю и не ломает работу остальных.
