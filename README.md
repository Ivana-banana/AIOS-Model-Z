# AIOS · трек 2 · Модель Z

Мультиагентная система управления фондом скважин с нейросетевыми суррогатными
моделями. Хакатон AIOS (ПАО «Татнефть»). Целевая функция — максимум ЧДД (NPV) при
соблюдении технологических ограничений.

Результат работы системы: `wells_schedule.inc` (управляющие последовательности) и
заявленное значение ЧДД, которое организаторы независимо перепроверяют одним
расчётом на полной гидродинамической модели.

**Что заявляется сейчас: 13 133,8 млн руб.** при базовом сценарии 11 851,8 —
прирост +1 281,9 млн руб. (+10,8 %). Файл `runs/matched-0995/wells_schedule.inc`,
прогон 24.08 на четырёх процессах MPI. Число получено эталонным расчётчиком
организаторов из того же прогона, что и файл, и воспроизводится шестью командами
— они и все оговорки к числу собраны в `docs/submission.md`.

**Наш расчёт сверен с расчётом организаторов.** 30.08 они опубликовали базовый
сценарий Модели Z в двух симуляторах, и на нём наш прогон лёг между ними: 5 207,7

## Установка

**Что нужно иметь до начала:** Python **3.11 или новее** (проверено на 3.14), Git
и около 300 МБ на диске. Для гидродинамического расчёта дополнительно нужен OPM
Flow или Docker (раздел «Расчёт в Docker»); без них ставится и проверяется всё,
кроме самого прогона.

Окружение лежит прямо в корне проекта (`Scripts/`, `Lib/`) и в репозиторий не
попадает. На чистой машине:

```powershell
py -3 -m venv .venv          # именно -3, а не -3.11: подойдёт любая 3.11+
.venv\Scripts\activate
pip install -r requirements-dev.txt
```

```bash
python3 -m venv .venv         # Linux и macOS
. .venv/bin/activate
pip install -r requirements-dev.txt
```

До 23.08 здесь стояло `py -3.11`, и на машине без ровно этой версии команда
отвечала «Requested Python version (3.11) not installed» — проверено буквальным
исполнением (`docs/clean-clone-check.md`).

**`requirements.lock` на Windows не поставится.** Он снят на Linux и несёт хэши
колёс той платформы: `pip install --require-hashes -r requirements.lock`
завершается «THESE PACKAGES DO NOT MATCH THE HASHES». Lock нужен для
воспроизведения **среды образа**, а не рабочего места; на Windows ставьте
`requirements-dev.txt`.

`requirements.txt` — рантайм решения (то, что попадает в Docker-образ),
`requirements-dev.txt` — плюс тесты, линтер и инструменты разбора материалов.

Материалы организаторов лежат в репозитории (`materials/`), искать их по каналу
не нужно. Распаковать дек:

```powershell
Expand-Archive materials\Model_Z_final_OPM.zip -DestinationPath vendor
Rename-Item vendor\Model_Z Model_Z_OPM
```

```bash
unzip -q materials/Model_Z_final_OPM.zip -d vendor -x "__MACOSX/*"
mv vendor/Model_Z vendor/Model_Z_OPM
```

Второй аргумент `Rename-Item` — **имя**, а не путь. До 23.08 здесь стояло
`vendor\Model_Z_OPM`, и команда падала с «Cannot rename the specified target,
because it represents a path or device name»: инструкция не исполнялась буквально.

Опись материалов и что из них извлечено — `materials/README.md`. Записей встреч
там нет: они по 500-800 МБ и в GitHub не помещаются, вместо них — расшифровки в
`docs/method/transcripts/`.

## Расчёт в Docker

Симулятор и рантайм одной командой — так же поднимается облачная машина под
пакетные прогоны:

```bash
docker build -t aios -f docker/Dockerfile .
python scripts/build_case.py
docker run --rm -v "$PWD:$PWD" -w "$PWD" aios \
    scripts/run_flow.sh runs/base/RUN.DATA 4 --parsing-strictness=low
python scripts/export_rows.py runs/base
```

Дек организаторов в образ не кладётся — монтируется томом.

Две детали, без которых прогон не пойдёт (обе выяснены на первом расчёте 16.08):

- **том монтируется по тому же пути, что и на хосте** (`-v "$PWD:$PWD"`, а не
  `/work`) — собранный `RUN.DATA` ссылается на файлы дека абсолютными путями;
- **`--parsing-strictness=low` обязателен** — дек содержит `PINCHREG`, которого
  OPM Flow не поддерживает, и со строгим разбором отказывается считать. Что это
  меняет в физике и почему число из такого прогона нельзя заявлять организаторам
  — `docs/experiments.md`.

Полный расчёт истории занимает около 11 минут на 8-ядерной машине (4 процесса
MPI). Про железо и оценку для слабых машин — `docs/setup-simulator.md`.

## Проверка

```powershell

```

`pytest` гоняет и наши тесты, и тесты эталонного расчётчика организаторов — они
часть нашего прогона, а не чужие.

Сверка базового сценария с расчётом организаторов (симулятор не нужен, считается
готовая выгрузка):

```powershell

```

Печатает расхождение по ЧДД и по каждой статье годовой раскладки. Эталон —
`docs/reference/`, наша сторона считается тем же расчётчиком организаторов.

Обучение суррогата на обоих пакетах DoE (сценарии из разных CSV автоматически

```powershell

python scripts/run_doe.py runs/doe-injection 4 -- --parsing-strictness=low
python scripts/build_dataset.py --run-root runs/doe-injection --out data/dataset-injection.csv
python scripts/train_surrogate.py --dataset data/dataset.csv data/dataset-levels.csv data/dataset-injection.csv

После прохождения порога качества запустить цикл на обученной модели:

python scripts/run_cycle.py --surrogate-model artifacts/surrogate.joblib
```

## Сквозной прогон

Одной командой, без ручных шагов между ними (требование ТЗ п. 3.2.3) — там, где
установлен симулятор, то есть в Docker-образе проекта или на Linux:

```bash
python scripts/run_all.py --flow-args=--parsing-strictness=low
```

Перед передачей пакета одной командой проверяются все позиции допуска — девять
из ТЗ плюс лицензионная. Проверка ничего не достраивает и вернёт ненулевой код, пока на
диске нет итогового расписания или обученного артефакта. Простого наличия файла
недостаточно: расписание разбирается, проходит ограничения и совпадает по md5 с
заявкой, а модель проходит порог качества:

```bash
python scripts/check_package.py \
  --schedule runs/matched-0995/wells_schedule.inc \
  --model artifacts/surrogate.joblib
```

В день отправки используйте короткий стоп-лист `docs/submission-day.md`: пакет
не уходит, пока все шесть проверок не дали указанный там результат.

Пять шагов: собрать кейс → посчитать базовый на ГГДМ → пройти цикл и собрать
расписание → посчитать получившийся сценарий → заменить прогноз полным расчётом.
Заявляемым числом считается только то, что напечатал последний шаг.

Флаг `--parsing-strictness=low` не зашит в скрипт намеренно: он меняет физику
расчёта (дек содержит неподдерживаемый `PINCHREG`) и обязан быть виден в команде.
`--dry-run` печатает план шагов на любой машине, включая Windows без симулятора.

Те же шаги по отдельности, если нужно вмешаться в середине:

```powershell
python scripts/build_case.py runs/base          # собрать кейс из дека
```
```bash
scripts/run_flow.sh runs/base/RUN.DATA 4 --parsing-strictness=low   # посчитать (Linux, OPM Flow)
```
```python
from aios import config, economics, margin, summary

settings = config.load()
rows = summary.monthly_rows("runs/base/RUN", fluids=settings.fluids)
assert not summary.sanity_problems(rows)
print(economics.compute_npv(rows, headers=economics.REQUIRED_COLUMNS,
                            start_date=settings.economics.start_date.isoformat()).chdd_m)
print(margin.shutdown_candidates(rows, margin.Norms.from_file())[:5])
```

## Главное правило

ЧДД считается **только** эталонным расчётчиком организаторов
(`vendor/CHDD_PYTHON/`). Своей формулы ЧДД в проекте нет и быть не должно:
расхождение заявленного значения с их пересчётом означает дисквалификацию.
Подробности — в `CLAUDE.md`.
