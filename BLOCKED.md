## 0.2-бис. Кэш демо-объяснений: нужен один прогон с ключом (04.09)

**Что нужно:** один запуск цикла на машине, где есть учётные данные модели, с
`[explain].enabled = true` и `cache_dir = "artifacts/explanations"`. Всё
остальное готово.

**Зачем.** ТЗ п. 3.1 требует языковую модель в ядре слоя интерпретируемости. У
проверяющего нет ни ключа, ни сети, поэтому слой отвечает шаблоном — и
требование ТЗ на его машине не видно вовсе. `explain()` читает кэш **раньше**,
чем проверяет `enabled`: закоммиченный кэш покажет настоящий ответ модели с
подписью «из кэша», без ключа и без вызова.

**Что уже сделано (Р-196).** Правило `.gitignore` разбито — каталог
`artifacts/explanations/` теперь коммитится, веса и метрики по-прежнему нет.
Поведение «кэш раньше `enabled`» и происхождение файла (имя модели, совпадение
отпечатка с именем файла) закреплены тестами.

**Чего делать нельзя.** Написать содержимое кэша руками или собрать шаблоном:
это выдало бы наш текст за ответ модели. Файл пишется только на пути `llm`, уже
после проверки чисел, — и тест это стережёт.

**Кому.** Машине с ключом; на этой его нет (`YANDEX_API_KEY` не задан,
`[explain].enabled = false`).

## 0.4. Суррогат по закачке хуже линейной модели — решение за человеком (03.09)

**Что нужно:** решить, что делать с прогнозом закачки у обученного суррогата.

**Измерение.** На `artifacts/surrogate-speed.joblib` (24 сценария, локальный
артефакт этой машины) по `WWIT_Diff`:

| Модель | MAE | R² отклика |
|---|---:|---:|
| MLP | 17,11 | 0,20 |
| линейный бейзлайн | 12,39 | 0,56 |

По жидкости и нефти MLP линейную обыгрывает (MAE 43,7 против 58,3 и 18,3 против
25,4), по закачке — проигрывает.

**Почему это важно.** Совместный поиск двигает **нагнетатели первыми**
(`optimise.choose_joint_rates`), а планировщик режет расписание по воде. То есть
решения по закачке принимаются на прогнозе, который хуже тривиального.

**Что сделано машиной.** `R²`-ворота теперь смотрят и на закачку (отвергнут
модель, которая отклик не объясняет вовсе). Сравнение «MLP обязан побить
линейную по MAE» осталось на жидкости и нефти: включение закачки отвергает
существующий артефакт целиком, а это решение с деньгами, а не сторож (Р-178).

**Три варианта, между которыми выбирает человек:**

1. **брать по закачке линейную модель** — разнести `kind` по целям; честно и
   дёшево, но ломает единый артефакт;
2. **доучить** на пакете DoE по нагнетателям (он есть: `runs/doe-injection`,
   12 сценариев) и перемерить;
3. **принять как есть** и записать в отчёт: закачку всё равно режет планировщик
   по коридору, а не суррогат.

**Что нужно от человека:** выбрать вариант. Первый и третий — минуты, второй —
прогон обучения. До выбора действует третий, и он назван в отчёте.

## 3. Как считается баланс воды (новый вопрос, 16.08)

**Что нужно:** уточнить у организаторов формулировку ограничения по закачке.

**Почему возникло:** мы поняли их ответ («дополнительной воды на объекте нет,
закачиваем ту, что подняли») как «накопленная закачка ≤ накопленная добытая
вода». Прогон показал, что при таком прочтении ограничение **отвергает саму
историю месторождения**: в историческом сценарии закачано 13 158 тыс. м³ при
добытой воде около 5 200 тыс. м³ — превышение в 2,5 раза. Применённое к нашему
сценарию, оно срезало закачку в 4,7 раза и обрушило ЧДД на 78 %
(`docs/experiments.md`, запись от 16.08).

*Сверка 18.08, закрыто:* эта пара — за **всю историю дека с 1991** (вода 5 164
тыс. м³, отношение 2,55), а измеренное ниже отношение 2,32 — за **расчётное окно
с 2007** по паре 11 671 / 5 038,2. Оба набора верны, период просто не был
подписан; подтверждено прогоном 18.08 (`docs/experiments.md`). В документах для
жюри стоит пара расчётного окна — на нём и считается ЧДД.

**Варианты прочтения, между которыми нужен выбор:**
1. баланс считается не по накопленному, а помесячно;
2. учитывается вода, возвращающаяся из пласта (закачка циркулирует);
3. ограничение вообще не количественное, а про «не завозить воду извне».

**Уточнение после разбора (16.08, критик).** Скорее всего, это не вопрос к
организаторам, а наш дефект: `aios/balance.py` сравнивает закачку с **добытой
водой**, тогда как при заводнении закачка компенсирует **отобранный объём в
пластовых условиях** — то есть нефть вместе с водой, да ещё с поправкой на
объёмные коэффициенты. При таком счёте историческое соотношение (13 158 против
отбора около 11 000 тыс. м³ жидкости) выглядит нормальной компенсацией около
100–120 %, а не нарушением в 2,5 раза.

Тогда ответ организаторов «дополнительной воды на объекте нет» означает «не
рассчитывайте на новый водозабор», а не «закачка ≤ добытая вода».

**ПРОВЕРЕНО 18.08 — предположение верное.** Проверка компенсации написана
(`aios.balance.compensation_problems`), объёмные коэффициенты измерены по деку
(`Bв = 1,0000`, `Bн` = 0,9862…1,0078, размах 2,2 %). На историческом сценарии:

- буквальное прочтение (закачка / добытая вода) — 2,32, то есть нарушение;
- компенсация (закачка / отобранная жидкость) — **1,29**, то есть 129 %, обычная
  величина для заводнения с поддержанием давления.

История проходит вторую проверку без нарушений — значит формулировка найдена
правильно (`docs/experiments.md`).

**ЗАКРЫТО 24.08 (Р-61 и Р-101).** Применяется компенсация с потолком 1,30, и
заявляемый сценарий её проходит — не «в пределах допуска», а без единого года
превышения. Прежний кандидат превышал потолок на 0,013 п.п.; соблюдение стоило
19,1 млн руб. и было куплено осознанно. Прочтение `produced_water` осталось в
конфиге одной строкой на случай, если организаторы имели в виду его.

Ниже — исходная формулировка вопроса.

**Что было нужно от человека:** решение, какую проверку применять на сдаче.
Мы не знаем, какое прочтение имели в виду организаторы. Обе доступны, применяемая
по умолчанию не менялась: подменить одну другой молча значит изменить ЧДД (цена
вопроса — те самые −1878 млн руб.) без решения человека.

**Внешняя опора получена 21.08 (`docs/manus/vrr-water-balance.md`).** Разбор по
нормативным и отраслевым источникам говорит следующее, и это меняет вес сторон:

- отраслевой показатель — компенсация отбора закачкой (VRR) **в пластовых
  объёмах**, то есть знаменатель — отобранная жидкость с объёмными
  коэффициентами, а не добытая вода. Это ровно наше прочтение (б);
- обязательной нормы вида «закачка ≤ добытая вода» **не существует**: проверено
  по Правилам подготовки ПТД (приказ Минприроды №639 от 20.09.2019, п. 6.15.5) и
  Порядку размещения вод (№490/09, действует с 01.09.2024). Нормируются источник,
  качество, проектные давления и **максимальный годовой объём**, а не кратность к
  добытой воде;
- превышение закачки над собственной добытой водой — обычное дело, оно
  покрывается сеноманской, пресной или поверхностной водой; фраза «дополнительной
  воды на объекте нет» ограничивает **источник**, а не отношение объёмов;
- но и обратное отчёт не подтверждает: устойчивое отношение «закачка / добытая
  вода» 2–2,5 при обводнённости 85–95 % соответствует поверхностной компенсации
  1,7–2,4 против практических 1,0–1,2. Для зрелого объекта это не рядовой режим,
  и на защите его придётся объяснять — у нас объяснение есть, компенсация 1,29.

Прямого ответа «(а) или (б)» отчёт не даёт: он отвечает «нормируется не это».

**РЕШЕНО 21.08 (Р-61): применяем компенсацию, потолок 1.3.** Правило вынесено в
конфигурацию (`limits.water_balance_rule`), прежнее прочтение осталось под именем

исторической компенсации объекта, а не взят с запасом.

**Что ещё не сделано:** прогон цикла с новым правилом. На машине, где правка
сделана, нет Docker и Ubuntu в WSL — полный расчёт отсюда не запускается. До
прогона эффект правки на ЧДД цикла остаётся гипотезой.

## 4. Потянет ли система ППД полуторакратную закачку (новый вопрос, 16.08)

**Что нужно:** узнать у организаторов, есть ли ограничение по мощности системы
поддержания пластового давления — КНС, водоводы, подготовка воды.

**Почему возникло:** лучший найденный сценарий (`runs/inject20`) даёт
**+1790.6 млн руб. (+15,1 %)** к базовому за счёт увеличения закачки на 48 %
(17 254 против 11 671 тыс. м³). Гидродинамически он корректен: предел давления
нагнетания 300 атм соблюдён, отношение закачки к добытой воде даже ниже
исторического. Но наш стенд не видит поверхностного обустройства вовсе — в
`CLAUDE.md` это прямо записано как явление, которое мы не проверяем.

**Чем это грозит:** если КНС не тянет такой расход, весь прирост нереализуем, и
заявлять его нельзя. Если ограничение есть в виде числа — оно ложится в
`config.toml` рядом с пределом по жидкости, и оптимизация идёт под него.

**Что дальше:** до ответа держим два сценария — «агрессивный по закачке» и
консервативный. Механизм готов: `max_field_injection_m3_per_day` в `[limits]`
при нуле выключен, а после подстановки числа планировщик ограничивает каждый шаг
и показывает срез в UI. Заблокировано только само значение мощности.

**СНЯТО 21.08 расчётом, а не ответом организаторов.** Вопрос был задан в
масштабе, которого у Модели Z нет: 11 671 и 17 254 тыс. м³ — накопленные объёмы
за 224 месяца, а не годовые. Фактически (`python docs/manus/ppd-rescale.py` по
`runs/base/rows.csv`) закачка по объекту — **1 934 м³/сут** в 2024 году на
41 нагнетательной скважине, а сценарий даёт **2 860 м³/сут**, то есть
**+925 м³/сут** (+39 м³/ч, +0,34 млн м³/год).

Такой прирост — это доли одного насосного агрегата: весь объект вместе со
сценарием укладывается в 0,66 агрегата ЦНС-180 или в два агрегата ряда ЦНС-63.
Дополнительная электрическая мощность при фактических устьевых давлениях
(медиана 179 атм, p90 232 атм, предел 300 атм) — **269–451 кВт**,
энергия — 2,4–4,0 ГВт·ч/год. Коллектор при скорости ≤ 1 м/с — внутренний диаметр
205 мм. Приёмистость на скважину растёт с 47 до 70 м³/сут при историческом
максимуме 245 м³/сут по отдельной скважине, то есть внутри уже освоенного
диапазона.

Вывод: мощность ППД лимитом для нашего сценария не является, и число в
`max_field_injection_m3_per_day` подставлять не из чего — ограничение не
достигается. Чего расчёт **не** доказывает: фактического состава оборудования
на объекте мы не знаем (насосы могут быть меньшего ряда и без резерва), а
равномерное масштабирование уставок ×2.0 поднимает максимум по отдельной
скважине с 245 до ~490 м³/сут — вот это и есть настоящий вопрос к приёмистости
конкретных скважин, а не к КНС. Методика расчёта и справочные ряды — в
`docs/manus/ppd-capacity.md`, ограничения его вводных — в `docs/manus/README.md`.

**Что нужно:** рабочий ключ Anthropic API на любой из машин — достаточно одного
настоящего вызова.

**Зачем.** Это последнее требование допуска (ТЗ п. 3.1, «слой интерпретируемости
с языковой моделью в ядре»), закрытое наполовину: слой написан, покрыт 26
тестами, выведен в интерфейс, но все проверки идут на подставном клиенте.
Запроса к реальной модели не было ни разу, и до него слой честно считается
написанным, а не рабочим — так и записано в отчёте.

**Что проверено без ключа:** отказ по выдуманному числу, пересчитанный процент,
разделитель тысяч, даты, кэш по отпечатку фактов, невозможность закэшировать
отвергнутый ответ, все три состояния на странице цикла. То есть логика проверена
полностью; неизвестна только реакция на живой ответ модели.

**Состояние:** `ANTHROPIC_API_KEY` не задан ни в окружении машины Б, ни в
конфигурации (`[explain] enabled = false` — намеренно, чтобы проверяющий запускал
пакет без наших учётных данных).

**Проверено 20.08 на машине Б (ключа по-прежнему нет, вызов не имитировался):**

* `ANTHROPIC_API_KEY` не задан ни в окружении, ни в `.env` — состояние выше в
  силе;
* **пакета `anthropic` в окружении машины Б нет вовсе**, хотя он есть в
  `requirements.txt` (`anthropic==0.116.0`). Это отдельная от ключа причина, по
  которой живой прогон не состоялся бы, и машина, которая его выполнит, обязана
  сначала убедиться, что пакет установлен;
* модель в конфиге — `claude-opus-5`, `max_tokens = 1024`;
* **молчаливый откат к шаблону при включённом слое больше невозможен.** До правки
  `explain()` при `enabled = true` и непостроенном клиенте отдавал
  `source="template"` с пустой причиной — неотличимо от `enabled = false`, то есть
  неудачный живой прогон выглядел бы как успешный. Теперь это `template-failed` с
  названной причиной, и библиотека отличается от учётных данных.

**Проверено 22.08 на машине Б (задача Б18; ключа по-прежнему нет, вызов не
имитировался):**

* **пакет `anthropic==0.116.0` установлен** в окружение машины Б, импорт проходит.
  Отдельной от ключа причины, по которой живой прогон не состоялся бы, больше нет;
* **путь пройден целиком без ключа**: при `[explain] enabled = true` страница
  цикла отдала HTTP 200, числа цикла на месте, объяснение — шаблонное, причина
  названа словами прямо на странице: «Вызов языковой модели не состоялся:
  `TypeError: "Could not resolve authentication method…"`». Прогон не упал, кэш
  при отказе не пишется. Данные прогона синтетические (выгрузки ГГДМ на машине Б
  нет): проверялся путь слоя, а не экономика;
* **где всплывает какая причина — изменилось с установкой библиотеки.**
  `anthropic.Anthropic()` без учётных данных **не падает**: конструктор
  откладывает разрешение ключа до запроса, и отказ приходит уже из
  `messages.create`. Сетевого запроса при этом не происходит. Для слоя это тот же
  `template-failed` с названной причиной — но ветка «клиент не построен» теперь
  ловит не пустой ключ, а испорченный профиль или неверный `base_url`; записано
  в `aios/explain.py`;
* **побочная находка: живой вызов мог случиться сам собой.** С установленной
  библиотекой тест «включён, но не дозвонился» строит настоящего клиента, и на
  машине, где ключ есть, каждый `pytest -q` уходил бы к живой модели настоящим
  запросом. Теперь тест снимает у себя `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`
  и `ANTHROPIC_PROFILE`, а `base_url` уводит на закрытый порт — проверено с ключом
  в окружении: запрос не уходит;
* **ключ в репозиторий попасть не может** (проверено, а не предположено): в
  `config.toml` и в коде его нет, файла `.env` нет ни в дереве, ни в истории git,
  и с 22.08 `.env` и `.env.*` закрыты `.gitignore` — **до этого не были**;
  `python-dotenv` в окружении есть, но ни один наш модуль его не вызывает, то есть
  ключ читается только из окружения. Кэш `artifacts/explanations` хранит ровно три
  поля (`text`, `model`, `fingerprint`) и целиком лежит под игнорируемым
  `/artifacts/`.

**Оговорка про кэш, которую нужно решить владельцу.** Раз `/artifacts/` в
`.gitignore`, сохранённое объяснение по умолчанию не уедет ни в репозиторий, ни в
пакет сдачи — значит, фраза «кэш делает результат воспроизводимым и без ключа»
верна только если файл кэша положить в пакет руками
(`git add -f artifacts/explanations/<отпечаток>.json`). Без этого проверяющий
получит шаблон, а не объяснение модели.

**Что дальше: последовательность живого вызова.** Выполняется на машине, где есть
выгрузка `runs/base/rows.csv` (сейчас это А), в каталоге репозитория.

1. Убедиться, что библиотека на месте:

   ```
   python -c "import anthropic; print(anthropic.__version__)"    # 0.116.0
   ```

   Другой ответ или `ImportError` — `pip install -r requirements.txt`.

2. Ключ — только в окружение текущей сессии, ни в какой файл:

   ```
   $env:ANTHROPIC_API_KEY = "sk-ant-..."      # PowerShell
   export ANTHROPIC_API_KEY=sk-ant-...        # bash
   ```

   И одна строка в `config.toml`, секция `[explain]`: `enabled = false` →
   `enabled = true`. `git diff config.toml` обязан показать ровно эту строку и ни
   одного ключа.

3. Поднять интерфейс и открыть страницу цикла — слой выведен только туда:

   ```
   python -m uvicorn aios.web.app:app --port 8000
   ```

   `http://127.0.0.1:8000/run/base/cycle`, блок «Почему система решила так».

**Что считать успехом.** Оба пункта, иначе живого вызова не было:

* строка «Чем получено: **языковой моделью** (`claude-opus-5`), проверка чисел
  пройдена»;
* появился файл `artifacts/explanations/<отпечаток>.json` с тем же отпечатком,
  что напечатан на странице.

Два других исхода — тоже результат, и записывать их надо так же честно:
«шаблоном: **вызов модели не состоялся**» — до модели не дошли, причина названа
тут же на странице; «шаблоном: **ответ модели отвергнут**» — вызов прошёл, но
модель ввела число, которого нет в расчёте, и проверка сработала как задумано.

**После прогона:** вернуть `enabled = false` (проверяющий запускает пакет без
наших учётных данных), убрать ключ из окружения, записать прогон в
`docs/experiments.md`. Оговорка «на живом API не гонялся» снимается из
`docs/report.md` (п. 4 раздела ограничений) и `docs/tz-compliance.md` только
после настоящего ответа модели — и только вместе с решением по кэшу выше.

### 7.1 (исходно). Транзитивные зависимости не зафиксированы

Прямых пакетов 14: 8 рантайма (`requirements.txt`) и 6 инструментов
(`requirements-dev.txt`), все с `==`. Но resolver тянет около шестидесяти, и
NumPy, pandas, SciPy приходят транзитивно — через `resdata` и `scikit-learn`.
На машине Б 22.08 разрешились NumPy 2.5.2, pandas 3.0.5, SciPy 1.18.0 (те же
версии, что видел внешний resolver 21.08), но это **Windows и Python 3.14**, а
поставка — Linux и системный Python образа. Lock, снятый здесь, описывал бы не ту
среду, поэтому он не снят вовсе, а не снят «примерно».

Что сделать на машине с образом:

```bash
docker run --rm -v "$PWD:$PWD" -w "$PWD" aios bash -lc '
  pip install pip-tools &&
  pip-compile --generate-hashes --output-file requirements.lock requirements.txt &&
  pip check'
```

`pip-compile` резолвит под тот интерпретатор, в котором запущен, — поэтому
запускать его надо **внутри образа**, а не рядом с ним. Готовый `requirements.lock`
ставится в сборке через `pip install --require-hashes -r requirements.lock`;
до тех пор `docker/Dockerfile` ставит `requirements.txt`, и это записано честно.

### 7.2. Состав образа: версии OPM, их лицензии, SBOM, проверки Dockerfile

**ЧАСТИЧНО ЗАКРЫТО 24.08 без Docker.** Версии и лицензии сняты не из образа, а из
установки того же PPA в WSL Ubuntu 24.04 — базы, из которой образ и собирается:

| Пакет | Версия | Лицензия |
|---|---|---|
| `libopm-simulators-bin` | 2026.04-1~noble | GPL-3.0+ (плюс GPL-2.0+, BSL-1.0, ODbL/DbCL на данные) |
| `libopm-common` | 2026.04-1~noble | GPL-3.0+ / GPL-3.0 (плюс BSD-2-Clause, LGPL-2.1) |
| `libopm-grid` | 2026.04-1~noble | **GPL-3.0+** — формула `or later` подтверждена |
| `libopenmpi3t64`, `mpi-default-bin` | 4.1.6-7ubuntu2, 1.15build1 | BSD-3-Clause |

Этим закрыта и отдельная открытая формулировка: у `opm-grid` стояло «GPLv3,
формула не подтверждена» — `copyright` самого пакета даёт `GPL-3.0+`.
`THIRD_PARTY_NOTICES.md` заполнен, источник в нём назван прямо.

**Что осталось и без Docker не берётся:** SBOM образа, его digest, хэши
Debian-пакетов и `docker buildx build --check`. Разница между «в образе» и «в том
же дистрибутиве из того же PPA» невелика, но она есть, и выдавать одно за другое
мы не будем.

```bash
# 1. Версии пакетов, попавших в образ (в первую очередь libopm-*).
docker run --rm aios dpkg-query -W -f='${binary:Package}\t${Version}\n' | sort > image-packages.tsv

# 2. Лицензионные файлы OPM и MPI из самого образа.
docker run --rm aios bash -lc 'for p in libopm-simulators-bin libopm-common libopm-grid mpi-default-bin; do
    echo "== $p"; cat /usr/share/doc/$p/copyright 2>/dev/null | head -40; done'

# 3. Версия симулятора и digest образа — то, чем подписаны числа отчёта.
docker run --rm aios flow --version
docker image inspect aios --format '{{index .RepoDigests 0}} {{.Id}}'

# 4. Проверки самого Dockerfile (не выполнялись ни разу).
docker buildx build --check -f docker/Dockerfile .

# 5. SBOM и происхождение (разрешённым в организации сканером).
docker buildx build --pull --no-cache --provenance=mode=max --sbom \
  --metadata-file build-metadata.json -t aios:$(git rev-parse --short HEAD) \
  -f docker/Dockerfile --load .
```

**Что считать закрытием:** заполненные поля в `THIRD_PARTY_NOTICES.md` (версии
OPM-пакетов), лицензионные файлы OPM в `LICENSES/`, `requirements.lock` в
репозитории, чистый `docker buildx build --check` и записанный digest образа.

**Чего не делать:** не подставлять правдоподобные версии и хэши. Пустое поле
видно, выдуманное — нет.
