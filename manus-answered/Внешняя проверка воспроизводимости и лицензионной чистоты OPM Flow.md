# Внешняя проверка воспроизводимости и лицензионной чистоты OPM Flow

**Дата проверки:** 21 августа 2026 года. **Объект:** пять приложенных файлов (`README.md`, `setup-simulator.md`, `onboarding-team.md`, `requirements.txt`, `requirements-dev.txt`). **Граница проверки:** исходный код, `docker/Dockerfile`, `.dockerignore`, lock-файлы, содержимое материалов заказчика, собранный образ и журналы запусков не были приложены; их фактическое содержание не утверждается и не проверялось.

> Я не юрист; ниже приведён рабочий лицензионный анализ, а не формальное юридическое заключение. Перед внешней поставкой Docker-образа, архива с материалами заказчика или публичным релизом его должен проверить квалифицированный юрист с учётом договоров и применимого права.

### Конфликты и незакреплённые зависимости

Проверка `pip install --dry-run --ignore-installed --report` завершилась без сообщения resolver о конфликте в доступной проверочной среде Python 3.12. Она выбрала NumPy 2.5.2, pandas 3.0.5 и SciPy 1.18.0; `torch` не выбран, поскольку ни один пакет из данного набора его не требует. Этот результат означает лишь, что **объявленные ограничения разрешимы на дату проверки**, а не доказывает отсутствие runtime- или ABI-конфликтов в коде AIOS.

Слабое место — не прямые пины, а их неполнота. `resdata` объявляет зависимости `numpy`, `pandas`, `cwrap`, `natsort`, `typing_extensions`, `resfo-utilities>=0.4.0`; `scikit-learn` — NumPy, SciPy, `narwhals` и `threadpoolctl`. Через `faster-whisper` добавляется независимый набор нативных ML-библиотек. Следовательно, одинаковый `requirements.txt` в разные даты не задаёт идентичную среду. Нужен скомпилированный lock-файл с хэшами, зафиксированными индексом/временем и отдельной матрицей для Linux/Windows, если Windows сохраняется в поддержке.

> **Пакеты без пина:** среди строк, обозначающих пакеты, — **нет**. Строка `-r requirements.txt` в `requirements-dev.txt` только включает другой файл и не является зависимостью. При этом **46 транзитивных пакетов** в разрешённом графе не имеют пинов в исходных requirements.

## Что не выполнимо буквально на чистой машине

Инструкции содержат много полезных эксплуатационных наблюдений, но не образуют единственного детерминированного сценария. В таблице перечислены именно шаги, которые нельзя исполнить буквально без внешнего знания или самостоятельной подстановки.

| Шаг/команда | Почему нельзя выполнить буквально | Минимальное исправление |
|---|---|---|
| `py -3.11 -m venv .venv` и `.venv\Scripts\activate` | Требует Windows, установленный Python Launcher и именно Python 3.11; установка Python и проверка `py -3.11 --version` не описаны. | Назвать ОС, минимальную версию Python, ссылку/способ установки и добавить preflight-команду. |
| `pip install -r requirements-dev.txt` | Не фиксирует транзитивные версии и хэши; команда предполагает доступный `pip` правильного окружения. | Использовать `python -m pip install --require-hashes -r requirements.lock`; добавить lock и wheelhouse либо индекс. |
| `unzip ...`, `mv ...`, `Expand-Archive ...`, `Rename-Item ...` | Предполагаются `unzip` либо PowerShell, точная внутренняя структура ZIP и наличие места. Нет SHA-256 и idempotent-проверки. | Добавить manifest входных файлов с SHA-256, проверку layout и скрипт `bootstrap-materials`. |
| `docker build ...` | Предполагает Docker daemon, BuildKit, доступ к базовому registry, файл `docker/Dockerfile` и права пользователя. Сам Dockerfile не приложен. | Дать установки Docker/Buildx, `docker version`, preflight и закреплённый Dockerfile. |
| `docker run ... scripts/run_flow.sh ...` | Нужны Bash, OPM Flow, MPI, корректный `$PWD`, доступ к монтированию, возможная настройка `/dev/shm`. В WSL-инструкции позднее указан обязательный `--shm-size=2g`, но в README его нет. | Дать одну платформенно-явную команду, например отдельные Linux и WSL варианты, с проверкой `flow --version`. |
| Установка через PPA | Нужны `sudo`, сетевой доступ, Ubuntu 24.04/26.04, `software-properties-common`, доверие к ключу PPA. `apt` не закрепляет версию Flow 2026.04. | Явно поддержать только Ubuntu 24.04/26.04, закрепить версию пакета/снимок и записать fingerprint ключа. |
| WSL-команда с `/mnt/c/.../AIOS` | `...` не является путём, а Windows-диск и имя дистрибутива различаются у пользователя. | Использовать параметризированную переменную с проверкой существования пути и инструкцией для пробелов. |
| Проверка `ruff check . && pytest -q` | Вложенные исходники и тесты не приложены; отсутствуют ожидаемые число тестов, версии ОС/MPI и эталонные output-хэши. | Добавить `make verify`/`run_all.py` с минимальным fixtures-набором, ожидаемыми checksums и кодами завершения. |
| Заявление о работе контейнера | В одном файле сказано «сборка ещё ни разу не выполнялась», в другом — что она успешна. Нет CI-лога, image digest, Git commit или артефакта. | Указать дату, commit, digest образа, SBOM и ссылку/вложение CI-лога. |
| Вендоренный расчётчик и материалы заказчика | Лицензия, авторское право, режим конфиденциальности и разрешение на передачу не приложены. | Не включать в публичный архив до письменного разрешения; хранить реестр происхождения и прав. |

## Лицензии и условия поставки

### Состав GPL-риска

Flow находится в репозитории `opm-simulators`, который прямо называет себя репозиторием OPM Flow и декларирует GPL v3+; Flow зависит как минимум от `opm-common` и `opm-grid`. Официальный порядок сборки OPM также показывает `opm-common → opm-grid → opm-simulators`. [18] [19] [20]

| Компонент | Лицензионный статус из первоисточника | Практическое следствие для пакета |
|---|---|---|
| OPM Flow / `opm-simulators` | README ветки Flow 2026.04: GPL 3; бейдж — GPL v3+. [18] | При передаче бинарника/образа с Flow применимы условия GPLv3 к этому covered work. |
| `opm-common` | GPLv3+ («version 3 or later»). [19] | Сохранять лицензию и notices; изменения в самом компоненте должны быть обозначены. |
| `opm-grid` | В релизной ветке есть текст GNU GPL v3. В проверенных источниках не найдена отдельная формула `only`/`or later`. | Не записывать в SBOM точнее, чем подтверждено; подтвердить по точному Debian-пакету/исходникам, попавшим в образ. |
| `opm-models` | Исторический GPL v2-or-later модуль, помеченный как deprecated и интегрированный в `opm-simulators`. [21] | Не считать его отдельной зависимостью Flow 2026.04 без SBOM. Если он фактически входит в образ, лицензию учитывать отдельно. |
| `resdata==6.3.3` | PyPI указывает `GPL-3.0`; это прямая runtime-зависимость. [2] | Лицензионный анализ Docker-образа нельзя ограничивать одним OPM Flow. |

> «[C]onvey the machine-readable Corresponding Source» — условие передачи object code по GPLv3, §6. [22]

**Docker-образ.** Передача Docker-образа получателю — типичный случай передачи (*conveying*) копии объектного кода. Для Flow, `opm-common`, `opm-grid` и `resdata`, которые фактически попали в образ, следует как минимум: сохранить применимые copyright/license/no-warranty notices, включить копию соответствующей лицензии, обозначить собственные патчи к GPL-компонентам и предоставить либо сопроводить соответствующим исходным кодом способ §6 GPLv3. Удобный практический вариант — положить в релиз `sources/` или дать рядом с образом бесплатный стабильный URL на точные исходники и скрипты сборки, версии и хэши которых совпадают с образом.

**Собственный Python-код.** Нельзя по приложенным документам юридически установить, является ли весь AIOS одним производным произведением GPL-компонентов или независимыми программами в агрегате. GPLv3 отдельно говорит, что включение covered work в агрегат из отдельных независимых работ само по себе не распространяет GPL на другие части (§5). Однако граница зависит от фактической архитектуры — импорта/линковки, способа взаимодействия, модификаций и применимого права. До поставки закрытого исходного кода рядом с Flow/resdata этот вопрос нужно отдать на точечную юридическую проверку; Docker как формат упаковки сам по себе эту границу не решает.

**Результаты расчёта.** Числовые `rows.csv`, ЧДД, `.UNSMRY` и графики не становятся GPL-материалами автоматически только потому, что их создал Flow: это прямо ограничено §2 GPLv3. Но это не даёт права публиковать входной дек, эталонный расчётчик, данные заказчика или результаты, если их использование/распространение ограничено договором, авторским правом, коммерческой тайной или правилами хакатона.

**Код и материалы заказчика.** Сам факт передачи заказчиком не доказывает право включить его в архив, Docker context или публичный Git-репозиторий. До включения нужен документированный правообладатель и письменное право как минимум на хранение, модификацию, передачу команде/организатору и — отдельно — публичную публикацию, если она планируется. При отсутствии права на публикацию материал должен быть исключён из публичного релиза и передаваться отдельно только разрешённому кругу получателей. Сохраните исходные notices и лицензию; не заменяйте их своим copyright. Это критично для `vendor/CHDD_PYTHON` и деков организатора.

### NOTICE и готовый раздел лицензий

Отдельный `NOTICE` не является универсальным требованием GPLv3. Он обязателен, когда это требует лицензия конкретного компонента: например, Apache-2.0 §4(d) требует перенести читаемые attribution notices из входного `NOTICE`, если он был в поставке. [23] Поэтому корректная структура — не один «магический» NOTICE, а набор: `LICENSE`, `LICENSES/`, `THIRD_PARTY_NOTICES.md`, SBOM и manifest источников. Для GPL-компонентов обязательно приложить полный текст GPL и не удалить исходные notices; для Apache-компонентов перенести их NOTICE.

Ниже — готовый текст для `THIRD_PARTY_NOTICES.md` или раздела «Лицензии» в README. Перед поставкой заполните поля в квадратных скобках по SBOM; не оставляйте их вымышленными.

```markdown
## Лицензии и сторонние компоненты

© [год/диапазон лет] [правообладатель собственного кода].

Этот пакет включает независимые сторонние компоненты. Их лицензионные тексты
находятся в каталоге `LICENSES/`; перечень версий, источников и хэшей — в
`sbom.cdx.json` и `THIRD_PARTY_NOTICES.md`.

| Компонент | Версия / идентификатор сборки | Лицензия | Исходный код / Corresponding Source |
|---|---:|---|---|
| OPM Flow (`opm-simulators`) | 2026.04, [точная версия Debian-пакета и хэш] | GPL-3.0-or-later — подтвердить по точному пакету | [стабильный URL / приложенный архив с SHA-256] |
| opm-common | 2026.04, [точная версия] | GPL-3.0-or-later | [стабильный URL / приложенный архив с SHA-256] |
| opm-grid | 2026.04, [точная версия] | GPLv3 — уточнить `only`/`or-later` по точному пакету | [стабильный URL / приложенный архив с SHA-256] |
| resdata | 6.3.3 | GPL-3.0 — подтвердить SPDX-суффикс по исходнику | https://github.com/equinor/resdata |

Если Docker-образ или бинарные формы GPL-компонентов передаются третьим лицам,
получателю одновременно предоставляется доступ к Corresponding Source этих
компонентов и к применимым скриптам сборки. Изменения в GPL-компонентах описаны
в `MODIFICATIONS.md` с датой, перечнем файлов и ссылкой на исходники.

Материалы заказчика и организаторов не входят в публичную поставку, если для
них нет отдельного письменного разрешения на публичное распространение. Их
происхождение, хэш, правообладатель, применимое разрешение и допустимый круг
получателей перечислены в закрытом `PROVENANCE_AND_RIGHTS.md`.
```

## Docker: что проверять перед сдачей

Поскольку Dockerfile не приложен, ниже приведён **контрольный стандарт**, а не утверждение о текущей реализации. Docker рекомендует фиксацию образа по digest, минимальные базовые образы, многостадийную сборку, `.dockerignore`, совмещение `apt-get update` и `apt-get install` в одной инструкции и очистку apt lists. [24] Build secrets нельзя передавать через `ARG` или `ENV`, поскольку они могут сохраниться в образе; используйте секретные BuildKit mounts. [25]

| Область | Что проверить в Dockerfile/образе | Доказательство при сдаче |
|---|---|---|
| База | `FROM` с tag **и** `@sha256:...`, платформой `linux/amd64` при необходимости; документированный процесс обновления digest | Dockerfile, digest, дата обновления |
| OPM и apt | Версия `libopm-simulators-bin`/Flow фиксирована; `apt-get update && apt-get install` в одном слое; после установки есть `flow --version` | build log, `flow --version`, lock/snapshot PPA |
| Python | Установлен lock с хэшами, используется `python -m pip`, нет неявного скачивания при runtime | `requirements.lock`, install log, `pip check` |
| Секреты | Нет токенов, ключей, `.env`, SSH-ключей, датасетов заказчика в context/слоях; `.dockerignore` исключает их | `docker history --no-trunc`, `docker image inspect`, ревизия `.dockerignore` |
| Контекст и размер | В context только нужные файлы; build-only инструменты исключены из runtime stage; размер измерен и объяснён | размер image, multi-stage Dockerfile |
| Запуск | `WORKDIR`, non-root user при допустимости, signal-friendly exec-form `CMD`, `--shm-size`/MPI/тома явно документированы | smoke test и запусковая команда |
| Происхождение | SBOM, provenance, image digest, commit и лицензии совпадают с поставляемым образом | `sbom.cdx.json`, `metadata.json`, `THIRD_PARTY_NOTICES.md` |
| Безопасность | Проверены CVE и неподдерживаемые пакеты; есть правило обновления образа | отчёт сканера с датой и исключениями |

Docker Buildx поддерживает быстрые build checks без исполнения сборки (`--check`) и генерацию SBOM/provenance через `--sbom` и `--provenance`. [26] [27] Минимальный набор команд для CI или предсдаточного прогона выглядит так:

```bash
# 1. Синтаксис и правила Dockerfile — без выполнения build-слоёв.
docker buildx build --check -f docker/Dockerfile .

# 2. Дополнительный линтер Dockerfile (например, Hadolint).
hadolint docker/Dockerfile

# 3. Чистая сборка с метаданными цепочки поставки.
docker buildx build --pull --no-cache \
  --provenance=mode=max --sbom \
  --metadata-file build-metadata.json \
  -t aios:[GIT_COMMIT] -f docker/Dockerfile --load .

# 4. Состав, слои, размер и риск утечки секретов.
docker image inspect aios:[GIT_COMMIT]
docker history --no-trunc aios:[GIT_COMMIT]
docker image ls aios:[GIT_COMMIT]

# 5. Smoke test именно поставляемого runtime.
docker run --rm aios:[GIT_COMMIT] flow --version
docker run --rm -v "$PWD:$PWD" -w "$PWD" --shm-size=2g aios:[GIT_COMMIT] \
  python -m pytest -q

# 6. SBOM/CVE: использовать разрешённый в организации сканер, например Syft/Trivy,
# и сохранить отчёты рядом с релизом.
```

## Сопоставление с чек-листами воспроизводимости

NeurIPS требует раскрывать ограничения, предположения, код, данные, инструкции, вычислительные ресурсы, гиперпараметры и статистические детали. [28] ACM SIGIR, применяя ACM policy 1.1, требует единый артефакт с инструкциями от чистой ОС, зафиксированные Python-зависимости, тег версии, доступные данные и независимое воспроизведение главных результатов для уровня *Results Reproduced*. Он также рекомендует контейнерный образ, а не только Dockerfile, и готовые данные для этапов дольше 24 часов. [29]

| Пункт чек-листов | Текущее покрытие по приложенным документам | Самое дешёвое закрытие |
|---|---|---|
| Доступный идентифицируемый артефакт | Частично: названы репозиторий и материалы, но нет релизного тега, DOI/архива, commit и manifest | Тег `vX.Y`, release archive, `SHA256SUMS`, commit и `CITATION.cff` |
| Инструкция от чистой ОС | Частично: много деталей, но несколько противоречивых путей и внешних предположений | Один проверенный `bootstrap → verify → run` для Ubuntu 24.04 и отдельно WSL, с preflight |
| Полная среда | Нет: прямые пины есть, транзитивные и хэши отсутствуют | Lock + `--require-hashes` + wheelhouse или OCI digest |
| Данные и права | Нет: нет manifest/deck hash и подтверждения прав заказчика | `DATA_MANIFEST.md` с хэшами, лицензиями, ограничениями, контактным владельцем |
| Воспроизведение результата | Не подтверждено: документы противоречиво описывают число прогонов и сборку | Скрипт `make reproduce-baseline`, ожидаемые FOPT/ЧДД/rows SHA, независимый запуск вторым человеком |
| Ресурсы и длительность | Частично: есть измерения CPU/RAM/времени, но не единая среда и лог | Таблица «commit → образ → Flow/MPI → CPU/RAM → команда → wall time → result» |
| Метод и ограничения | Частично: риск `PINCHREG` описан хорошо, но нет единого раздела limitations | `LIMITATIONS.md`: игнорирование PINCHREG, PPA/WSL, допуски, применимость результатов |
| Модель/ML-эксперимент | Нет подтверждаемого комплекта: отсутствуют seed, хэши CSV, параметры обучения и версии артефакта модели | `experiment.yaml`, фиксированный seed, dataset/model hashes, command и метрики held-out |
| Лицензионная воспроизводимость | Нет: GPL-компоненты известны, но нет SBOM/NOTICE/исходников | SBOM, `LICENSES/`, `THIRD_PARTY_NOTICES.md`, `MODIFICATIONS.md`, реестр прав |

## Предсдаточный чек-лист

Ниже приведён чек-лист из 20 пунктов. Пункты 1–8 обычно дают наибольший эффект при минимальной стоимости и должны быть закрыты до экспериментальной оптимизации.

- [ ] 1. Зафиксировать Git commit, релизный тег и неизменяемый архив исходников; записать SHA-256 архива.
- [ ] 2. Выпустить lock-файл всех Python-зависимостей с хэшами и задокументировать индекс/зеркало; выполнить `pip check` после установки.
- [ ] 3. Проверить установку в новой VM/контейнере без ранее установленных пакетов на заявленных Python 3.11 и 3.12 либо убрать неподдерживаемую платформу.
- [ ] 4. Добавить один `bootstrap`-скрипт, который проверяет Python, Docker, BuildKit, `flow`, MPI, свободное место и рабочий каталог.
- [ ] 5. Зафиксировать SHA-256 деки, ZIP, эталонного расчётчика и всех обязательных входных файлов в `DATA_MANIFEST.md`.
- [ ] 6. Получить письменное подтверждение прав на хранение, модификацию и передачу каждого материала заказчика; исключить непубличные файлы из Git и Docker context.
- [ ] 7. Устранить документальные противоречия о Docker-сборке и выполненных прогонах, добавив даты, commit, image digest и ссылки на логи.
- [ ] 8. Сформировать «claim → команда → выходной файл → проверка/допуск» для базового FOPT, ЧДД, расписания и web-платформы.
- [ ] 9. Запустить `python -m ruff check .` и `python -m pytest -q` в чистой среде; сохранить число тестов, версии и полный лог.
- [ ] 10. Запустить Docker build checks и линтер Dockerfile; сделать нарушения ошибками CI.
- [ ] 11. Закрепить каждый `FROM` по digest и записать платформу образа; собирать с `--pull --no-cache` в релизной CI.
- [ ] 12. Зафиксировать версию OPM Debian-пакета, PPA fingerprint и способ получения именно Flow 2026.04; добавить `flow --version` в smoke test.
- [ ] 13. Проверить `docker history --no-trunc`, image inspect и `.dockerignore` на секреты, `.env`, ключи, персональные пути и материалы заказчика.
- [ ] 14. Измерить размер образа; исключить build-зависимости и dev-инструменты из runtime через multi-stage, если это совместимо с Flow.
- [ ] 15. Сформировать SBOM и provenance образа, сохранить image digest и результаты CVE-сканирования с датой.
- [ ] 16. Выполнить базовый расчёт в поставляемом образе с нужными `--shm-size`, томом и MPI; сохранить `RUN.DATA`, лог и `rows.csv`.
- [ ] 17. Автоматически проверить отсутствие игнорированных ключевых слов, ненулевой FOPT, sanity-проверки rows и согласованность заявленного ЧДД.
- [ ] 18. Для суррогата зафиксировать seed, CSV/model hashes, split, параметры MLP, версии библиотек, метрики и допустимый порог.
- [ ] 19. Положить в пакет `LICENSE`, `LICENSES/`, `THIRD_PARTY_NOTICES.md`, `MODIFICATIONS.md`, SBOM и инструкции получения Corresponding Source GPL-компонентов.
- [ ] 20. Дать второму участнику без истории проекта выполнить `bootstrap`, тесты и один baseline; приложить его лог, характеристики машины и отклонение результата.
