# Что мы сдаём и чем это подтверждено

Один документ на вопрос «что уходит организаторам». Числа здесь не пересказаны
своими словами — они взяты из `docs/experiments.md`, запись **«Лучший сценарий
воспроизведён: ЧДД 13 645.7, файл и число из одного прогона (21.08)»**. Если
число здесь и там разошлось — верен журнал, а этот документ отстал.

Исключение одно и подписано на месте: результаты прогона тестов приходят не из
журнала экспериментов, а из `JOURNAL.md` — там ведётся проверка репозитория, а
не расчётов.

## 1. Заявляемое число и файл

| | Значение |
|---|---|
| **ЧДД** | **13 645,7 млн руб.** |
| считал | эталонный расчётчик организаторов, `vendor/CHDD_PYTHON/`, версия `7.0.2-negative-row-filter` |
| дисконт от | 01.01.2007 |
| базовый сценарий **того же прогона** | 11 856,2 млн руб. |
| прирост | **+1 789,5 млн руб. (+15,1 %)** |
| сдаваемый файл | `runs/inject20/wells_schedule.inc` — 1,53 МБ, 371 шаг (1994-11 … 2025-09), 103 скважины |
| предполётная проверка файла | пройдена, отказов и предупреждений нет |
| прогон | 21.08, машина А, OPM Flow 2026.04 в WSL2, 6 процессов, 12 мин 08 с |
| исключённых отрицательных строк | 0 |

**Файл и число получены из одного прогона** — это не формальность. Пара «файл от
одного расчёта, число от другого» и есть механизм дисквалификации: организаторы
делают **один** расчёт нашего файла и сравнивают ЧДД с заявленным.

Ранее в отчёте стояли числа 16.08 (13 642,4 при базовом 11 851,8). Они устарели:
расхождение 3,3 млн руб. (0,02 %) — измеренный дрейф сборки кейса за пять дней,
пока три машины меняли склейку расписания. Дрейф записан в журнале, а не списан.

**Файла нет в репозитории.** `runs/` под `.gitignore` (крупные бинарники в git не
кладём, `GIT.md`), поэтому файл не хранится, а **воспроизводится командой** —
см. раздел 3.

## 3. Как повторить число

Три команды, ровно те, что записаны в журнале прогонов:

```bash
python scripts/build_scaled_case.py runs/inject20 --production 1.5 --injection 2.0
bash scripts/run_flow.sh runs/inject20/RUN.DATA 6 --parsing-strictness=low
python scripts/export_rows.py runs/inject20
```

1. **сборка** — `scripts/build_scaled_case.py` масштабирует наши шаги поверх истории дека;
   история до начала управления не трогается. Ограничение методики 500 м³/сут
   соблюдается внутри сборки, ноль означает остановку, а не открытую скважину с
   нулевым дебитом;
2. **расчёт** — `scripts/run_flow.sh` запускает OPM Flow; `6` — число процессов MPI;
3. **выгрузка и счёт** — `scripts/export_rows.py` пишет `rows.csv` в 14 колонках контракта
   и печатает ЧДД. Считает его **только** вендоренный расчётчик организаторов;
   своей формулы ЧДД в проекте нет, и это проверяется тестом паритета до
   последнего знака (`abs(a−b) ≤ 1e-9`).

**Почему `--parsing-strictness=low` стоит в команде, а не внутри скрипта.** Флаг
меняет физику расчёта: дек содержит неподдерживаемый `PINCHREG`. Флаг, меняющий
результат, обязан быть виден в команде, которой прогон воспроизводится — скрытых
зависимостей быть не должно (п. 3.5 ТЗ).

**Что подставляет проверяющий своё:** дек Модели Z (в репозитории его нет) и
`Нормативы_ЧДД.xlsx` — файл организаторов, лежит в вендоренном расчётчике как
есть. Пути к деку задаются в `config.toml`, имена файлов дека нигде не зашиты: на
валидационном кейсе они будут другими.

## 4. Чего это число **не** доказывает

Честный разбор ограничений — часть сдачи, а не оговорка мелким шрифтом.

1. **Реализуемость закачки.** В сценарии она на 48 % выше исторической, а
   мощность системы ППД наш стенд не моделирует вовсе (`BLOCKED.md`, п. 4).

2. **Больше половины закачки в этом сценарии задаёт не наше расписание, а предел
   давления 300 атм.** Скважина на пределе берёт столько, сколько пропускает
   призабойная зона, а её считает модель околоскважинного пространства — то самое
   место, где OPM и тНавигатор расходятся сильнее всего. Замер 21.08:

   | Сценарий | ЧДД, млн руб. | Прирост | **Закачки на пределе** | Медиана BHP |
   |---|---:|---:|---:|---:|
   | история | 11 856,2 | — | 15,9 % | 231,7 |
   | ×1.5 / ×1.3 | 12 783,2 | +7,8 % | 32,4 % | 260,5 |
   | ×1.5 / ×1.6 | 13 271,8 | +11,9 % | 44,0 % | 290,8 |
   | **×1.5 / ×2.0** | **13 645,7** | **+15,1 %** | **58,1 %** | **300,0** |

   Прирост и потеря контроля растут вместе, а отдача насыщается: первый шаг стоит
   +927 млн, последний — +374 млн при вдвое большей доле, отданной пределу. В
   заявляемом сценарии **медианный нагнетатель сидит ровно на 300 атм**.

   Выбор сценария — решение владельца, и оно ещё не зафиксировано. Более
   осторожный ×1.6 отдаёт 374 млн руб. (2,7 % прироста) и снижает долю на пределе
   с 58 % до 44 %. Данные для выбора собраны; сам выбор пойдёт в
   `docs/decisions.md`.
3. **Разрыв с тНавигатором.** Считали мы в OPM Flow, проверять будут в
   тНавигаторе. Организаторы закладывают в допуск «пару процентов» разницы
   симуляторов; наш стенд эту разницу измерить не может.
4. **Это не результат агентов.** Сценарий — равномерное масштабирование, тупой
   бейзлайн, с которым обязаны сравниваться усложнения. Цикл МАС на сегодня даёт
   **хуже**: −72,9 % на тривиальном суррогате и −79,4 % на прошедшем порог
   (`docs/report.md`, «Что не закрыто», п. 9). Мы сдаём то, что лучше, и говорим
   об этом прямо.
5. **Открытые вопросы организаторам** — четыре, все в `BLOCKED.md`: формат файла
   (п. 1), формулировка баланса воды (п. 3), мощность ППД (п. 4), плюс ключ API
   для живого вызова слоя интерпретируемости (п. 6).
6. **Место в рейтинге.** По п. 4.3 ТЗ считается ЧДД на **тестовом кейсе**
   организаторов, а не на Модели Z. Эти +15,1 % показывают, что подход находит
   деньги, но не место в таблице.

## 5. Проверяющему: от чистого клона до того же числа

```bash
git clone <репозиторий> aios && cd aios
pip install -r requirements-dev.txt
python -m pytest -q          # ожидается: падений 0
python -m ruff check .
```

**Падений быть не должно ни одного.** Проверка чистым клоном 20.08
(`JOURNAL.md`, «сдаваемый репозиторий собирается и запускается»): 589 тестов,
0 падений, 7 пропусков — все семь названы, пять требуют дека Модели Z, два —
Node.js для межъязыковых сверок вендоренного расчётчика. Число тестов растёт с
каждым днём (на 21.08 их 608), поэтому сверять надо не его, а нули в падениях и
ошибках. Тесты вендоренного расчётчика (16 штук) идут в том же прогоне — они
часть нашей проверки, а не чужие.

Пропусков на клоне семь, а на машине с распакованным деком — два: разница и есть
те пять тестов, которым дек нужен.

Дальше нужен дек и симулятор:

1. распаковать поставку организаторов в каталог, указанный в `config.toml`
   (`README.md`, раздел «Установка»);
2. собрать образ: `docker build -t aios -f docker/Dockerfile .` — в нём OPM Flow
   и рантайм;
3. выполнить три команды раздела 3.

Расчёт занимает около 12 минут на шести процессах. Расхождение в последних знаках
между машинами возможно и ожидаемо; расхождение в разы означает, что подставлен
другой дек или потерян флаг `--parsing-strictness=low`.
