# Симулятор: установка и первый прогон

Решение команды: считаем **OPM Flow** на Linux. Организаторы допускают это явно и
закладывают расхождение с тНавигатором «в пару процентов» в допуск.

## Где именно считать

Windows 10 Enterprise LTSC 2019 — сборка 17763 (версия 1809). WSL2 требует 1903+,
Docker Desktop современных версий — 21H2+. Штатный путь «OPM Flow под WSL2» на этой
машине не заводится. Вторая ОС отпадает по условиям команды. Остаётся два рабочих
варианта, и они не исключают друг друга:

1. **Виртуальная машина VirtualBox с Ubuntu 24.04 прямо здесь.** VirtualBox не
   требует WSL2 и Hyper-V, ему достаточно VT-x, который у Haswell-процессора есть.
   Отдельная машина и переустановка ОС не нужны. Годится, чтобы получить первый
   базовый прогон и убедиться, что весь контур сходится.
2. **Облачная Linux-VM для пакетных прогонов.** Нужна для датасета суррогата:
   там счёт идёт на сотни расчётов, и локальным железом это не закрывается ни в
   каком виде (см. ниже).

Разбор результатов (`aios/summary.py`, `resdata`) работает и на Windows: после
прогона достаточно забрать `.UNSMRY` и `.SMSPEC`.

## Сколько это считает

Что известно про задачу и про машину:

| | |
|---|---|
| Активных ячеек | 240 664 из 547 638 (43,9 %) |
| Отчётных шагов | 371 месячный, 11.1994 → 09.2025 |
| Физика | трёхфазная нефть-вода-газ с растворённым газом, 15 равновесных регионов |
| Скважин | 103 |
| Процессор | Intel Pentium G3220, **2 ядра / 2 потока**, Haswell 2013, без AVX2 |
| Память | 12 ГБ (для 240 тыс. ячеек хватает с запасом) |

Точную цифру даст только прогон, но порядок величины оценивается уверенно: модель
такого размера на современных 8–16 ядрах считается десятками минут, а этот Pentium
медленнее в разы — два потока вместо шестнадцати и отсутствие AVX2 в линейной
алгебре. Ожидание: **единицы часов на один полный прогон**, ночью — нормально,
пакетом по сотне — исключено.

Отсюда разделение труда: локальная VM — для первого базового прогона и отладки
контура; облако — для DoE под суррогат.

## Что сократит счёт вдвое

Управление начинается с 01.01.2007, а история 1991–2006 у всех сценариев одна и та
же — её незачем пересчитывать в каждом прогоне. Стандартный приём: посчитать
историю один раз, сохранить рестарт на 01.01.2007 и дальше стартовать каждый
сценарий с него (`RESTART` + `SKIPREST`). Это убирает 146 шагов из 371, то есть
около 40 % работы каждого прогона, и ровно столько же — из счёта за облако.

Делать это стоит **после** первого успешного полного прогона: рестарт, снятый с
неверного расчёта, тиражирует ошибку по всему датасету.

## Установка OPM Flow (Ubuntu 22.04 / 24.04)

```bash
sudo apt-add-repository ppa:opm/ppa
sudo apt-get update
sudo apt-get install -y libopm-simulators-bin
flow --version
```

Для параллельного счёта дополнительно `sudo apt-get install -y mpi-default-bin`.

## Подготовка кейса

Материалы организаторов распаковываются в `vendor/Model_Z_OPM/` (см.
`docs/materials.md`). Дальше:

```bash
python scripts/build_case.py runs/base
scripts/run_flow.sh runs/base/RUN.DATA
```

Базовый кейс = история как есть, только с нашей SUMMARY-секцией: `Model_Z_summary.inc`
в поставке пустой, и без своих векторов симулятор не выгрузит ничего.

Свой сценарий:

```python
from datetime import date
from aios.run import build_case

case = build_case(
    "runs/scenario-01",
    "vendor/Model_Z_OPM",
    steps=my_steps,               # список ScheduleStep
    control_start=date(2007, 1, 1),
)
```

История до `control_start` сохраняется дословно — вместе с `COMPDAT`, задающим
вскрытия фонда во времени. Пересобирать её из разобранных структур нельзя: без
вскрытий скважины останутся без соединений с пластом, и симулятор об этом не
скажет — просто выдаст нулевую добычу.

## Разбор результата

```python
from aios import economics, summary

rows = summary.monthly_rows("runs/base/RUN")
problems = summary.sanity_problems(rows)
assert not problems, problems[:10]

result = economics.compute_npv(rows, headers=economics.REQUIRED_COLUMNS,
                               start_date="2007-01-01")
print(result.chdd_m)
```

## Что проверять на первом прогоне

Прежний главный риск снят самими организаторами: во второй поставке
(`Model_Z_final_OPM.zip`) тНавигаторовские `WELLTRACK` и `COMPDATMD` заменены
стандартным `COMPDAT`, аналитические ОФП `COREYWO` — табличным `SWOF`, а `LGR`
закомментирован с пометкой «OPM compatibility». Дек читается OPM Flow по
построению.

Это не повод принимать результат на веру. Симулятор не падает на том, чего не
понял, — он это пропускает и считает дальше. Проверяем три вещи:

1. в логе нет строк про игнорирование ключевых слов (`scripts/run_flow.sh`
   печатает их отдельным блоком);
2. `FOPT` на конец истории отличен от нуля и по порядку величины совпадает с
   ориентиром организаторов — около 4,8 млн т нефти (`docs/experiments.md`);
3. профили по нескольким скважинам похожи на историю, а не на прямую линию —
   смотрим глазами, а не по сводным числам.
