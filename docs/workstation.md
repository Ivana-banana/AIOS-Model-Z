# Рабочая машина: почему зависает и что с этим сделано

Снимок диспетчера задач от 08.09.2026 —
[`screenshots/2026-09-08-диспетчер-задач-python.jpg`](screenshots/2026-09-08-диспетчер-задач-python.jpg):
полтора десятка процессов `Python` по ~30 МБ, у всех **0 % CPU и 0 МБ/с диска**.
Это не «питон съел процессор»: процессы стоят в очереди и ничего не получают.

## Что за машина

| | |
|---|---|
| CPU | Intel Pentium G3220 @ 3,0 ГГц — **2 ядра, 2 потока**, без Hyper-Threading |
| RAM | 12 ГБ (свободно ~6,6 ГБ при открытом PyCharm) |
| Системный диск | **ST500DM002 — HDD**, 500 ГБ, не SSD |
| Антивирус | Kaspersky (32-бит), процесс `avp` |
| PyCharm | 2026.2 через Toolbox; рядом стоит неиспользуемый 2022.3.2 |

Узких мест два, и оба не про Python:

1. **Два ядра.** PyCharm при индексации занимает оба, и на отрисовку окна
   не остаётся ничего — система выглядит зависшей, хотя работает.
2. **Механический диск.** PyCharm читает проект, Kaspersky проверяет каждый
   прочитанный файл, Windows Search индексирует их же. На HDD очередь к диску
   вырастает до секунд, и всё, что ждёт диска (включая мышь и меню), замирает.
   Отсюда и «0 МБ/с» у питонов на снимке.

Объём, который перемалывался при каждом открытии проекта: `.venv` — 1,1 ГБ и
**18 361 файл** (torch, scipy, sklearn, ctranslate2, onnxruntime), `vendor` —
191 МБ (деки, включая `Model_Z_grid.inc` на 74 МБ одним текстовым файлом),
`materials` — 47 МБ, три записи встреч в корне — **1,8 ГБ**. Собственного кода
при этом 408 файлов.

## Что уже сделано (08.09.2026)

- **Индексация PyCharm сведена к своему коду.** В `.idea` было
  `<excludeFolder url="file://$MODULE_DIR$" />` — исключён весь корень проекта.
  Это глушило индексацию целиком вместе с автодополнением и навигацией по
  `aios/` и `scripts/`. Заменено точечными исключениями: `.venv`, `runs`,
  `artifacts`, `materials`, `vendor/Model_Z`, `vendor/Model_Z_OPM`,
  `vendor/portability`, `vendor/__MACOSX`, `data`.
  Индексируется 408 файлов вместо 19 039; `vendor/CHDD_PYTHON` остаётся
  проиндексированным — он часть нашего прогона тестов.
  Файл: `.idea/aios-track2.iml` (PyCharm переименовал модуль сам).
- **Куча PyCharm поднята с 1524 МБ до 2048 МБ.** Процесс держал 1287 МБ при
  потолке 1524 — то есть жил в постоянной сборке мусора, а GC на двух ядрах
  отбирает те самые ядра. Добавлен `-XX:SoftRefLRUPolicyMSPerMB=50`, чтобы кэши
  отпускались быстрее. Файл:
  `%APPDATA%\JetBrains\PyCharm2026.2\pycharm64.exe.vmoptions`
  (рядом лежит `.bak-20260908`). **Применяется только после перезапуска PyCharm.**
- **Windows Search отключён на тяжёлом.** Атрибут «не индексировать содержимое»
  (`attrib +I`) выставлен на `.venv`, `runs`, `artifacts`, `materials`, `vendor`
  и на три `*.webm` в корне.

## Что нужно сделать руками

1. **Перезапустить PyCharm** — иначе новая куча не применится, а исключения
   не пересоберут индекс. После запуска будет одна долгая переиндексация
   (уже по 408 файлам), дальше станет тихо.
2. **Исключения в Kaspersky.** Настройки → Угрозы и исключения → Управление
   исключениями → добавить как доверенные:
   - `C:\Users\Professional\PycharmProjects\AIOS\.venv`
   - `C:\Users\Professional\PycharmProjects\AIOS\runs`
   - `C:\Users\Professional\PycharmProjects\AIOS\vendor`
   - `C:\Users\Professional\AppData\Local\JetBrains`
   - `C:\Users\Professional\AppData\Roaming\JetBrains`

   Плюс в «Доверенные программы» — `pycharm64.exe` и `python.exe` из `.venv`.
   Это снимает проверку на каждое чтение файла — на HDD именно она и стоит дорого.
3. **Убрать записи встреч из проекта.** 1,8 ГБ `*.webm` в корне не нужны ни
   PyCharm, ни git (они в `.gitignore`), но их видит и антивирус, и любой обход
   каталога:
   ```powershell
   New-Item -ItemType Directory -Force "$HOME\Records\AIOS"
   Move-Item "$HOME\PycharmProjects\AIOS\*.webm" "$HOME\Records\AIOS"
   ```
4. **Снести PyCharm 2022.3.2** (`C:\Program Files\JetBrains\...`) — вторая
   IDE на той же машине держит свои кэши (74 МБ) и легко запускается по ошибке.

## Что осталось известным ограничением

- **Прогон симулятора на этой машине всё равно займёт обе ядра.** В `config.toml`
  стоит `processes = 2`, и это осознанно: числа в `docs/experiments.md` получены
  именно так, менять параметр молча нельзя. Пока идёт расчёт, машина будет
  неотзывчивой — это не поломка. Если нужно работать параллельно с прогоном,
  запускать его с `--processes 1` и записывать это в журнал экспериментов
  как отдельный прогон.
- **Замера «до/после» нет.** Изменения обоснованы состоянием машины (потолок
  кучи, объём индексации, тип диска), а не измеренным временем отклика:
  воспроизвести зависание по требованию не получилось — на момент проверки
  ни одного процесса `python` в системе не было.
- SSD решил бы задачу целиком, всё перечисленное — обход отсутствия SSD.
