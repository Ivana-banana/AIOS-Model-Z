# Задача: хакатон AIOS, трек 2

Сведено из онбординга, лекций и постов организаторов (исходники — `docs/method/`,
`docs/materials.md`). Всё, что здесь написано, — из материалов организаторов;
наши решения и интерпретации живут в `docs/decisions.md`.

## Что за хакатон

**AIOS** — «ИИ-центричная операционная система управления разработкой месторождения».
Организатор — ПАО «Татнефть» (Blue Sky Research). Призовой фонд 1 млн ₽, команды 3–5
человек, три недели разработки, два инженерных трека.

| | Трек 1 | **Трек 2 (наш)** |
|---|---|---|
| Модель | Y, ~46–49 скважин, 3 разлома | **Z, ~100–109 скважин** |
| Суррогатная модель | не требуется | **рекомендуется, влияет на оценку** |
| Использование ГГДМ | на каждой итерации | **только финальная проверка** |
| Проверка гипотез | напрямую через ГГДМ | **суррогат + финальный расчёт ГГДМ** |
| Фокус | корректность МАС | **корректность + масштабируемость + эффективность ресурсов** |
| Целевая функция | max NPV | **max NPV** |
| UI / веб-платформа | обязательна | **обязательна** |

## Что должна уметь система

- использовать суррогатные нейросетевые модели для прогноза динамики параметров
  разработки без запуска полной ГГДМ;
- вырабатывать управляющие воздействия на основе предсказаний суррогата;
- генерировать корректный файл управляющих последовательностей `wells_schedule.inc`;
- обеспечивать максимизацию NPV при расширенной постановке (больше скважин, сложнее
  конфигурация), сохраняя воспроизводимость и пригодность к проверке на полной ГГДМ;
- анализировать состояние месторождения и учитывать ограничения и возмущения;
- переводить скважины из добычи в закачку (ППД) для поддержания пластового давления;
- работать без ручного вмешательства после запуска.

Цикл МАС: **оценка состояния → диагностика → управляющее воздействие → проверка →
повторная оценка**. Допустимые воздействия (трек 2): открыть/закрыть скважину,
изменить режим добычи, перераспределить закачку, перевести скважину под закачку.

## Обязательный пакет материалов

Без полного пакета решение **к валидации не допускается**:

1. исходный код с логичной структурой каталогов;
2. документация: назначение, архитектура, установка и запуск, описание входных и
   выходных данных, параметры;
3. пошаговая инструкция по запуску (без ручной настройки сложной инфраструктуры);
4. файл конфигурации со всеми параметрами воспроизведения;
5. Docker-образ или материалы для сборки (рекомендуется);
6. результаты на тестовом кейсе: `wells_schedule.inc` + заявленное значение NPV;
7. git-репозиторий;
8. веб-платформа / UI с LLM-агентами в ядре;
9. для трека 2 дополнительно: суррогатная модель и её описание (архитектура,
   обучение, метрики).

## Регламент отбора в финал

Организаторы направляют каждой команде **валидационный кейс**: набор ограничений и
история разработки месторождения. Гидродинамические модели остаются прежними
(трек 2 — Model Z): **меняются условия задачи, а не объект**.

В отведённое время команда передаёт:

1. `wells_schedule.inc` — итоговый файл управляющих последовательностей, оптимальных
   при заданных ограничениях. Файл обязан быть совместим с расчётной моделью и
   пригоден к расчёту **без ручного редактирования**;
2. значение **ЧДД (NPV)**, полученное решением на этом кейсе.

Проверка: организаторы выполняют **один** расчёт полной гидродинамической модели на
нашем расписании и сравнивают полученный ЧДД с заявленным.

> ⚠️ Если значения расходятся — **команда дисквалифицируется**. Погрешность в пару
> процентов, обусловленная разницей симуляторов, заложена в допуск и нарушением не
> считается. Всё, что выходит за эти рамки, трактуется как неподтверждённый результат.
> **Один расчёт — одна попытка**, повторных прогонов не предусмотрено.

Проверить заранее: файл корректно читается моделью, а ЧДД посчитан по методике
организаторов (эталонный расчётчик — `vendor/CHDD_PYTHON/`).

Команды ранжируются по значению NPV. В финал проходят 20 % команд от числа
допущенных к валидации, но не более 10 команд.

## Финал и защита

- Организаторы независимо перезапускают расчёт на предоставленных управляющих
  последовательностях. NPV организаторов ≠ заявленный NPV → дисквалификация.
- Онлайн-защита: 7 минут презентации по архитектуре МАС + 5 минут вопросов жюри.
- Демонстрационный запуск решения во время защиты.

Критерии финальной оценки жюри:

| Критерий | Что смотрят |
|---|---|
| Корректность и воспроизводимость | NPV совпадает с независимой проверкой |
| Учёт ограничений | все технологические и физические ограничения соблюдены |
| Техническое качество | архитектура, структура кода, документация |
| Эффективность подхода | NPV против **референсного сценария** организаторов |
| Обоснованность алгоритмов | выбор БФМ, математика, методы обучения и оптимизации |
| Качество презентации | ясность, структура, демонстрация, ответы |

Дополнительные критерии трека 2: эффективность вычислительных ресурсов (скорость
решений без полного перебора), качество суррогата (согласованность с ГГДМ, обобщение
на новые сценарии), масштабируемость архитектуры МАС до 100+ скважин.

**Референсный сценарий** — заранее сформированный организаторами эталон, отвечающий
всем ограничениям и дающий близкий к оптимальному NPV. Используется как верхняя
граница качества при финальном ранжировании.

## Требования к воспроизводимости

- Повторный запуск в идентичной среде на тех же данных → сопоставимый результат.
- Нет скрытых зависимостей от внешних ресурсов, не поставляемых с решением.
- Нет неконтролируемых случайных параметров; seed зафиксирован в конфигурации.
- Решение пригодно для автоматической или полуавтоматической проверки.
- Нельзя подменять исходные данные организаторов собственными.
- Нет скрытых привязок к конкретному месторождению.

## Объект: Модель Z

- Eclipse-совместимый дек, сгенерирован тНавигатором v25.1; `METRIC`, `START 01 JUN 1991`.
- `DIMENS 91 102 59`, `WELLDIMS 137 109 2 137` — до 137 скважин, 109 соединений на
  скважину. По лекции — **109 скважин** под управлением.
- SCHEDULE: месячные шаги `DATES`, 11.1994 → 09.2025 (371 шаг), управление через
  `WCONPROD` (`LRAT`, ограничение по дебиту жидкости, `BHP` 50) и `WCONINJE`
  (`WATER`, `RATE`, `BHP` 300).
- Начало управления фондом по методике: **01.01.2007** для трека 2 (для трека 1 —
  01.01.2014); этот год — первый год дисконтирования.
- `Model_Z_summary.inc` **пустой** — SUMMARY под выгрузку пишем сами.
- Что важно понять (из лекции): целевая добыча при дефиците воды, удержание давления,
  запуск/остановка и перераспределение режимов, ремонты. Ожидаемое поведение агента —
  согласованные решения на уровне объекта, а не локальная оптимизация отдельных скважин.

## Симуляторы и открытые данные (ответ организаторов на вопрос команды)

Картины гидродинамики месторождения нужно **сгенерировать самим**: запустить симулятор
расчёта гидродинамики на выданной модели. Доступные симуляторы:

- **tNavigator** — при наличии лицензии у участников;
- **OPM Flow** — https://opm-project.org/?page_id=19 (открытый);
- **MRST** — https://www.sintef.no/projectweb/mrst/.

Открытые датасеты, которые могут пригодиться: OPM (opm-project.org/?page_id=559),
Equinor Volve (2008–2016), ORSD, Reservoir Models Dataset (hw.tpu.ru/en/dataset/).
